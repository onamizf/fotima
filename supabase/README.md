# Подключение реальных аккаунтов Supabase

Владелец подтвердил успешный запуск SQL и настройку URL. Вход включён; реальная доставка писем, вход и изоляция данных ещё требуют проверки. Проверки в artifacts/cloud-validation.json используют тестовые HTTP-ответы, а не настоящий Supabase. Проект заказчика: rjllssgpppsdjkpjzdrx. В src/cloud-config.js записаны только публичный адрес и Publishable key, предоставленные заказчиком. Серверных секретов в приложении быть не должно.

## 1. Таблица и доступ к собственным данным

1. В проекте Supabase открыть **SQL Editor** → **New query**.
2. Скопировать весь [setup.sql](setup.sql) в редактор.
3. Нажать **Run**. Ожидаемый результат — успешное выполнение без ошибок.
4. При ошибке остановиться и прислать текст ошибки без секретов. Не выключать RLS для обхода ошибки.

Файл создаёт таблицу lab_progress и функцию сохранения с номером версии. Политики RLS позволяют читать и изменять только строку собственного пользователя; анонимный доступ запрещён. Повторный запуск обновляет политики и функцию, не удаляя прогресс. Если таблица с таким названием ранее создана с иной структурой, требуется отдельная проверка, а не удаление пользовательских данных.

## 2. Почта и адрес сайта

В **Authentication → Sign In / Providers → Email** включить вход по почте и оставить подтверждение почты включённым. Разделы панели могут называться немного иначе.

В **Authentication → URL Configuration**:

- Site URL: `https://onamizf.github.io/fotima/`
- Redirect URLs: `https://onamizf.github.io/fotima/`
- Для отдельной локальной разработки при необходимости добавить точный используемый localhost-адрес. Не добавлять широкие wildcard-домены без необходимости.

Письма подтверждения и восстановления зависят от лимитов и настроек почтовой отправки Supabase. Бесплатный тариф не является обещанием неограниченной рассылки. Для широкого школьного использования может потребоваться отдельный SMTP и проверка его условий. Пока реальная доставка не проверена, не считать email-вход готовым.

## 3. Включение на сайте

После подтверждения успешного SQL и настройки адреса изменить `enabled: false` на `enabled: true` в [cloud-config.js](../src/cloud-config.js), проверить конфигурацию и опубликовать. После подтверждений владельца значение уже изменено на true. Это не демонстрационная авторизация.

После включения первым открывается регистрация; вкладка «Войти» доступна существующим пользователям. Регистрация без активной сессии показывает просьбу подтвердить почту, а не успех входа. Ссылка подтверждения/восстановления очищается от токенов в адресной строке. Сессия хранится в sessionStorage вкладки; пароль не записывается в localStorage, отчёты или файлы проекта. После закрытия вкладки может потребоваться новый вход.

## 4. Как устроено сохранение

Каждому user_id соответствует своя серверная строка и отдельная местная копия. Прежний прогресс без аккаунта не удаляется и не переносится автоматически. В настройках аккаунта его можно перенести явной командой с подтверждением. Это заменяет текущую попытку; перед заменой доступно скачивание JSON-копии.

Изменения отправляются с небольшой задержкой. При отсутствии сети они остаются в браузере; статус показывает проблему и даёт повторить сохранение. Копия браузера привязана к адресу сайта: данные с localhost не появляются автоматически на GitHub Pages.

Ревизия предотвращает незаметную перезапись новым устройством: при конфликте загрузить местную JSON-копию, затем явной командой загрузить данные аккаунта. Автоматического объединения одновременно выполненных опытов нет. JSON-скачивание — резервная копия; произвольный загрузчик файла в этом этапе не добавлен.

После выхода текущий пользователь не отображается, а его копия остаётся под отдельным ключом браузера для восстановления после следующего входа. На общем компьютере рекомендуется отдельный профиль или приватное окно; данные в localStorage не зашифрованы от человека с доступом к этому браузеру. Это учебный прогресс, не официальный аттестационный журнал.

Общий сброс в настройках очищает текущую попытку и синхронизирует пустой прогресс; он не удаляет аккаунт Auth. Удаление аккаунта пока выполняет администратор проекта через Supabase Authentication; связанная строка прогресса удаляется каскадно. Самостоятельное удаление и отдельная административная панель не реализованы.

## 5. Обязательная реальная проверка

| Действие | Ожидается | Фактический статус |
| --- | --- | --- |
| Выполнить setup.sql | Таблица и политики созданы | Владелец подтвердил Success |
| Зарегистрировать аккаунт A | Доставлено письмо и подтверждён адрес | Не проверено на реальном проекте |
| Прочитать часть теории и сохранить | Статус сохранения без ошибки | Не проверено |
| Войти A в другом браузере | Загрузился тот же прогресс | Не проверено |
| Создать аккаунт B | Нет данных A | Не проверено |
| Попытаться прочесть/обновить user_id A с токеном B | Нет доступа к строке A | Не проверено на реальном RLS |
| Изменить попытку на двух устройствах | Конфликт без незаметной потери | Проверено на тестовом API; реальный проект ожидается |
| Отключить сеть, внести изменение, вернуть сеть | Местная копия остаётся, отправка повторяется | Требуется реальная проверка |
| Восстановить пароль по письму | Пароль изменён, старый больше не подходит | Требуется реальная доставка письма |

Браузерные тесты: `LAB_TEST_BASE=http://127.0.0.1:8023/ python tests/cloud_e2e.py` в Bash среды разработчика с Playwright/Chromium. CLOUD_USE_SITE_CONFIG=1 включает использование настоящей публичной конфигурации сайта при подменённых API-ответах. Тестовый API проверяет логику клиента и компоновку, но не доказывает безопасность настоящих политик PostgreSQL, доступность сервиса или доставку писем. Запрос к реальному auth endpoint из облачной среды получил сетевой отказ 403 до соединения с проектом.
