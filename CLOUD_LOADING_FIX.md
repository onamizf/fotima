# Исправление тупика после входа

## Наблюдение

Заказчик показал страницу уже вошедшего пользователя с сообщением «Не удалось загрузить аккаунт». Это подтверждает успешную авторизацию, но не работу хранилища прогресса. Исходный клиент скрывал HTTP/код ошибки и блокировал все учебные экраны при неуспешном первом чтении базы.

## Изменения

- Ошибка загрузки отдельно показывает этап, HTTP-статус и код сервиса. Не выводятся пароли, токены, тело запроса, полные ответы сервера или пользовательские данные из payload.
- Объяснения различают отсутствие таблицы/функции, ошибку прав, несовместимую схему, сеть и общий сбой. Текст доступен на четырёх языках.
- Вошедший и проверенный через Auth пользователь после ошибки базы может явно выбрать «Продолжить на этом устройстве». Анонимный посетитель не получает эту возможность; при HTTP 401 новая кнопка не предлагается.
- В местном режиме на учебных экранах виден баннер: облачное сохранение не работает. Действия остаются в отдельной копии пользователя; автоматическая отправка до чтения серверной версии запрещена.
- При восстановлении связи неизвестная база ревизии не даёт молча перезаписать существующий серверный прогресс. Появляется конфликт; замена местной попытки облачной требует подтверждения. Скачать копию по-прежнему можно.
- Конфликт или ошибка уже загруженного аккаунта также видны через баннер со ссылкой на настройки.
- Подготовлен [read-only SQL для проверки таблицы, прав и RLS](supabase/check-progress.sql). Настройки защиты не отключались и данные сервера не удалялись.

## Проверка

`tests/cloud_load_failure_e2e.py`: воспроизведены успешный Auth + HTTP 404/PGRST205 на чтении прогресса, HTTP 403/42501 и HTTP 401. Проверены код без приватного тела ответа, местное продолжение, сохранение после перезагрузки, отсутствие преждевременного POST, конфликт с позднее обнаруженной серверной ревизией, отмена/подтверждение замены, четыре языка и 16 компоновок. Результат — [cloud-load-failure-validation.json](artifacts/cloud-load-failure-validation.json).

Повторно прошли клиентские сценарии аккаунтов `tests/cloud_e2e.py` и упаковка сайта `tests/site_package.py`. Backend во всех этих проверках подменён или явно отключён для отдельного тестирования локальных маршрутов, поэтому они не подтверждают работу настоящего RLS.

## Что ещё нужно установить

Точная причина сбоя базы у заказчика пока неизвестна: исходный снимок не содержал кода, а запросы к настоящему Supabase из облачной среды получили сетевой отказ CONNECT 403. Это другой отказ, не доказательство ошибки RLS проекта. После публикации нужен код из обновлённой страницы аккаунта. Не следует объявлять настройку настоящей базы исправленной по одному клиентскому тесту или предполагать, что нужно заново регистрироваться.
